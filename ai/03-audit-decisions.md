# Рішення за результатами AI-аудиту

## 1. Мета документа

У цьому документі зафіксовано рішення щодо трьох основних розбіжностей, виявлених під час AI-аудиту UML Component Diagram бібліотечної системи.

Основний процес — UC-03 «Видача книги».

## 2. Проблема №1 — Нові компоненти

**Зауваження AI:** у компонентній моделі додано Library API, ReaderService та BookService, яких не було окремо на sequence-діаграмах лабораторної №3.

**Рішення:** частково прийняти зауваження.

**Заплановане виправлення:** залишити ці компоненти, але пояснити їхню роль у специфікації та захисті.

Library API відповідає за приймання запитів від Library UI.

ReaderService відповідає за операції з читачами.

BookService відповідає за операції з книгами.

Ці компоненти є архітектурною деталізацією і не змінюють бізнес-правила UC-03.

## 3. Проблема №2 — Недостатня деталізація інтерфейсів

**Зауваження AI:** інтерфейси показані на діаграмі, але їхні операції не визначені.

**Рішення:** прийняти зауваження.

**Заплановане виправлення:** додати до компонентної моделі основні операції:

- ILibraryAPI — submitLoan().
- ILoanService — issueBook().
- IReaderService — findReaderById().
- IBookService — findBookById(), isBookAvailable().
- IReaderRepository — findById().
- IBookRepository — findById().
- ILoanRepository — findActiveLoan(), createLoan().
- IDataStorage — операції збереження та читання даних.

Це дозволить зрозуміти, які саме можливості надає кожен компонент.

## 4. Проблема №3 — Повідомлення та поточна дата

**Зауваження AI:** у попередніх лабораторних використовувалися Clock і повідомлення LoanIssued / LoanRejected, але на компонентній діаграмі вони не деталізовані.

**Рішення:** прийняти зауваження.

**Заплановане виправлення:**

1. Додати компонент Clock, який надає інтерфейс IClock з операцією today().
2. Показати залежність LoanService від IClock.
3. Уточнити, що результат операції передається через Library API до Library UI.
4. Передбачити в ILibraryAPI повернення результату LoanIssued або LoanRejected.

Clock розглядається як внутрішній компонент системи.

## 5. Зовнішні інтеграції

Окремі зовнішні Payment, SMS/Email та OAuth-сервіси не додаються.

У попередніх лабораторних немає підтвердженої вимоги використовувати ці інтеграції.

Бібліотекар залишається зовнішнім користувачем системи.

Якщо в майбутньому з'явиться вимога до автентифікації або надсилання електронних повідомлень, архітектуру можна розширити.
