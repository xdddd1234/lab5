# AI-аудит UML Component Diagram

## 1. Об'єкт перевірки

Лабораторна робота №5 — компонентна архітектура бібліотечної системи.

Процес: UC-03 «Видача книги».

Файли:
- `spec.md`
- `diagrams/library-components.puml`
- `diagrams/library-components.svg`

Аудит виконано на основі PlantUML-коду та специфікації, підготовлених у розмові. Фактичні файли GitHub і SVG-рендер окремо не перевірені.

## 2. Перевірка компонентів

У моделі передбачено такі компоненти:

- Library UI
- Library API
- LoanService
- ReaderService
- BookService
- ReaderRepository
- BookRepository
- LoanRepository
- Library Database

Основні архітектурні шари представлені: UI, API, бізнес-логіка, доступ до даних і база даних.

## 3. Перевірка межі системи

Компоненти розміщено всередині прямокутника Library System.

Бібліотекар знаходиться поза межею системи.

Це дозволяє відокремити користувача від внутрішніх програмних компонентів.

## 4. Перевірка provided/required-інтерфейсів

У діаграмі визначено інтерфейси:

- ILibraryAPI
- ILoanService
- IReaderService
- IBookService
- IReaderRepository
- IBookRepository
- ILoanRepository
- IDataStorage

Для кожного інтерфейсу вказано компонент, який його надає, і компонент, який його використовує.

Зауваження: операції інтерфейсів не деталізовані. Особливо це стосується IDataStorage, який використовують три репозиторії.

## 5. Перевірка залежностей

Основний ланцюг:

Library UI → Library API → LoanService.

LoanService залежить від ReaderService, BookService та LoanRepository.

ReaderService використовує ReaderRepository.

BookService використовує BookRepository.

Репозиторії звертаються до Library Database.

У запропонованій структурі немає очевидних циклічних залежностей.

## 6. Відповідність лабораторній №1

Library Database містить сутності:

- Reader
- Book
- Author
- Category
- Loan

Це відповідає переліку сутностей моделі даних.

Зауваження: на компонентній діаграмі не показано окремих сервісів для Author та Category. Для UC-03 це не обов'язково, але межі відповідальності потрібно пояснити.

## 7. Відповідність лабораторній №2

Архітектура підтримує чотири сценарії UC-03:

| Сценарій | Відповідальний компонент |
|---|---|
| SC-01 — успішна видача | LoanService, LoanRepository |
| SC-02 — книга вже видана | LoanService, LoanRepository |
| SC-03 — неправильна дата | LoanService |
| SC-04 — читача не знайдено | ReaderService, ReaderRepository |

Основні бізнес-правила можуть бути реалізовані в LoanService.

## 8. Відповідність лабораторній №3

У sequence-діаграмах використовувалися LibraryUI, LoanService та репозиторії.

У компонентній моделі додано Library API, ReaderService та BookService.

Це допустима архітектурна деталізація, але потрібно пояснити, що нові компоненти не змінюють бізнес-логіку UC-03.

Також потрібно уточнити, як LoanService отримує поточну дату, оскільки в лабораторній №3 використовувався Clock.

## 9. Відповідність лабораторній №4

Компонентна архітектура підтримує:

- отримання запиту від бібліотекаря;
- перевірку читача;
- перевірку книги;
- перевірку дати повернення;
- створення Loan;
- повернення результату операції.

Зауваження: повідомлення LoanIssued і LoanRejected у компонентній моделі не виділені як окремі інтерфейсні операції або події. Потрібно пояснити спосіб їх передавання через Library API.

## 10. Зовнішні інтеграції

Payment, SMS/Email та OAuth не включено до поточної архітектури.

Це не обов'язково помилка, оскільки в UC-03 немає підтвердженої потреби в таких інтеграціях.

Однак відсутність зовнішніх інтеграцій потрібно явно обґрунтувати в DEFENSE.md.

## 11. TOP-3 розбіжності

### Проблема 1. Нові компоненти порівняно з лабораторною №3

**Опис:** Library API, ReaderService та BookService не були окремими учасниками початкових sequence-діаграм.

**Ризик:** незрозуміло, як нова архітектура співвідноситься з попередньою моделлю взаємодії.

**Рекомендація:** описати ці компоненти як деталізацію архітектури та явно зіставити їх із попередніми учасниками.

### Проблема 2. Недостатня деталізація інтерфейсів

**Опис:** інтерфейси позначені, але їхні основні операції не наведені.

**Ризик:** важко перевірити, чи всі потрібні взаємодії підтримуються компонентами.

**Рекомендація:** визначити ключові операції інтерфейсів, зокрема createLoan, findReaderById, findBookById і findActiveLoan. Окремо уточнити контракт доступу до БД.

### Проблема 3. Неявний механізм повідомлень і часу

**Опис:** у лабораторних №3–4 використовувалися Clock і повідомлення про результат, але в компонентній моделі їх реалізація не пояснена.

**Ризик:** частина поведінки попередніх моделей не має явного архітектурного відповідника.

**Рекомендація:** визначити джерело поточної дати та спосіб передавання LoanIssued і LoanRejected через інтерфейси системи.

## 12. Загальний висновок

Запропонована компонентна модель охоплює основні архітектурні шари бібліотечної системи.

Межа системи, компоненти та залежності загалом визначені послідовно.

Для кращої узгодженості з попередніми лабораторними рекомендовано деталізувати інтерфейси, пояснити нові компоненти та уточнити реалізацію повідомлень і отримання поточної дати.

Ці висновки потрібно підтвердити перевіркою фактичного PlantUML-файлу та SVG.
