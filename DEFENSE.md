# DEFENSE — Лабораторна робота №5

## 1. Тема роботи

**UML Component Diagram — архітектура бібліотечної системи.**

Основний процес: UC-03 «Видача книги».

## 2. Мета роботи

Мета лабораторної роботи — побудувати компонентну архітектуру бібліотечної системи, визначити її основні модулі, інтерфейси, залежності та межу системи.

## 3. Опис архітектури

Систему поділено на п'ять архітектурних шарів:

1. **Presentation Layer** — Library UI.
2. **API Layer** — Library API.
3. **Business Logic Layer** — LoanService, ReaderService, BookService, Clock.
4. **Data Access Layer** — ReaderRepository, BookRepository, LoanRepository.
5. **Data Layer** — Library Database.

Library UI приймає дії бібліотекаря, Library API передає запити до бізнес-логіки, LoanService координує процес видачі книги, а репозиторії забезпечують доступ до даних.

## 4. Зв'язок із лабораторною №1

У лабораторній №1 було побудовано ER-модель із сутностями:

- Reader
- Book
- Author
- Category
- Loan

У компонентній архітектурі ці дані зберігаються в Library Database.

Для роботи з читачами, книгами та видачами передбачено відповідні репозиторії.

## 5. Зв'язок із лабораторною №2

У лабораторній №2 було визначено UC-03 «Видача книги» та чотири сценарії:

- SC-01 — успішна видача.
- SC-02 — книга вже видана.
- SC-03 — неправильна дата повернення.
- SC-04 — читача не знайдено.

У компонентній архітектурі основна відповідальність за виконання бізнес-правил належить LoanService.

Запис Loan створюється лише після успішного проходження перевірок.

## 6. Зв'язок із лабораторною №3

У лабораторній №3 були побудовані sequence-діаграми взаємодії LibraryUI, LoanService, репозиторіїв та Clock.

У компонентній моделі збережено ці основні ролі.

Додатково введено Library API, ReaderService та BookService для чіткішого розподілу відповідальності.

Це архітектурна деталізація попередньої моделі, а не зміна сценаріїв UC-03.

## 7. Зв'язок із лабораторною №4

Activity Diagram описує процес видачі книги:

1. Отримання запиту.
2. Перевірка читача.
3. Перевірка книги та її доступності.
4. Перевірка дати повернення.
5. Створення Loan за успішного результату.
6. Повідомлення про успіх або відмову.

Компонентна архітектура забезпечує виконання цих дій.

Результати LoanIssued і LoanRejected передаються від LoanService через Library API до Library UI.

## 8. Provided та Required Interfaces

На діаграмі визначено інтерфейси, через які компоненти взаємодіють між собою.

Наприклад:

- Library API надає ILibraryAPI, який використовує Library UI.
- LoanService надає ILoanService, який використовує Library API.
- Clock надає IClock, який використовує LoanService.
- Репозиторії надають інтерфейси доступу до відповідних даних.

Таке розділення зменшує залежність компонентів від конкретних реалізацій.

## 9. Межа системи та інтеграції

Усі програмні компоненти розміщені всередині межі Library System.

Бібліотекар є зовнішнім користувачем.

Інтеграції Payment, SMS/Email та OAuth не включено, оскільки в попередніх моделях UC-03 немає підтверджених вимог щодо їх використання.

## 10. Результати AI-аудиту

Під час аудиту було виділено три основні питання.

**Перше — узгодженість із sequence-діаграмами.**

У компонентній моделі з'явилися додаткові сервіси. Вирішено зберегти їх і пояснити як деталізацію архітектури.

**Друге — деталізація інтерфейсів.**

До моделі додано основні операції інтерфейсів, щоб показати їхню відповідальність.

**Третє — джерело поточної дати та передавання результатів.**

Додано Clock та IClock. Також уточнено шлях повернення LoanIssued або LoanRejected до Library UI.

## 11. Як використовувався AI

AI використовувався для попереднього аналізу архітектури, пошуку потенційних розбіжностей і підготовки рекомендацій.

Також AI допомагав готувати чернетки документації та PlantUML-код.

Остаточні рішення необхідно перевірити за вимогами лабораторної роботи та фактичними файлами проєкту.

## 12. Висновок

У лабораторній роботі побудовано компонентну модель бібліотечної системи.

Визначено основні компоненти, архітектурні шари, provided/required-інтерфейси, залежності та межу системи.

Модель пов'язана з ER-моделлю, Use Case, Sequence Diagram та Activity Diagram попередніх лабораторних робіт.
